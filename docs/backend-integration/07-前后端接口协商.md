# 07 前后端功能校验与接口协商

校验对象：`v3-kit/source`（前端，23 页 / 4 Tab）与 `services/assistant-api`（后端，12 条路径）。
时间：2026-10-23。所有数字为本机实跑，命令与输出见第 2 节。

## 1. 三条结论

1. **平台桥接这一层是通的。** 认证 → 隐式开户 → 建 Run → 启动工作流 → SSE 流式 → 取消 → 工具回调 → 记忆召回，15 项检查在真实 HTTP 上全部通过，包括分块到达与断点续传。
2. **业务域这一层几乎为零。** 23 页里只有 1 页（关于）完全不需要后端、4 页部分具备条件、18 页没有任何对应资源。现有后端证明的是"怎么接"，不是"接了什么"。
3. **两侧对同一件事的词不一样。** 前端用展示文本（`10月24日`、`'89'`、`进行中`），后端用可比较值（ISO 时间、Decimal、枚举）。这不是风格问题，是必须现在定的契约问题，见第 4 节。

## 2. 校验方法与实测结果

三层，各自能证明的东西不同：

| 层 | 命令 | 能证明 | 不能证明 |
|---|---|---|---|
| 单元/契约 | `pytest -q` | 34 个隔离规则 | 真实网络、流式、进程启动 |
| 真实 HTTP | `python scripts/e2e_check.py` | 两个进程、真实 SSE、真实头部 | 多机部署、并发压力 |
| 契约漂移 | `python scripts/check_contract.py` | 前端类型与后端 Schema 一致 | 运行时语义 |

### 2.1 真实 HTTP 端到端（`services/assistant-api/scripts/e2e_check.py`）

拉起 `nexus-stub`（模拟 NexusPilot 应用 API，真实端口）与 `assistant-api`（真实端口），用 `httpx` 走网络，不经进程内传输。

```text
[PASS] health                           api ok, nexus=personal_assistant
[PASS] api surface                      12 paths
[PASS] login rejects wrong password     401 unauthenticated
[PASS] login + me                       user=7bd3e7bf… fields=3
[PASS] ask requires session             401
[PASS] identity field in body rejected  422 extra field rejected
[PASS] create ask                       202 status=running run=run_stub_1
[PASS] SSE streaming                    5 frames, ids 1..5, spread=0.28s, ttfb=0.10s
[PASS] resume with Last-Event-ID        resumed at 4, got ['4', '5']
[PASS] run projection                   status=succeeded last_seq=5
[PASS] duplicate submit replays         replayed=true, same local run
[PASS] cancel                           cancelled
[PASS] business tools + replay          3 tools ok, note=1649e70b…, replay cached
[PASS] memory recall                    2 hits with sources
[PASS] upstream contract                9 upstream calls, no identity in any body

15/15 checks passed
```

几个值得单独说明的断言：

- **分块是真实的**：5 帧跨度 0.28s，首帧 0.10s。若上游一次性返回，跨度会接近 0。这条只有真实 HTTP 能测出来。
- **续传是真实的**：带 `Last-Event-ID: 3` 只收到 4、5，不是重放全部。
- **身份没有外泄**：逐条检查了 9 次上游调用的 JSON，没有任何请求体含 `user_id` 或 `principal_id`；当前头 `X-External-User-Id` 等于本地用户 id（`X-NexusPilot-*` 已移除）。
- **重复提交不产生第二次运行**：本地 `(user_id, idempotency_key)` 唯一，`replayed=true` 且 `local_run_id` 不变。

### 2.2 契约漂移（`scripts/check_contract.py`）

把 `v3-kit/source/src/api/contract.ts` 与后端生成的 OpenAPI 逐字段对比：

```text
AskRead                ok (9 fields, 7 required)
AskRequest             ok (2 fields, 2 required)
AskResponse            ok (5 fields, 4 required)
LoginRequest / LoginResponse / MeResponse / MemorySearchRequest   ok
8 个端点常量全部命中已注册路由
contract ok: 7 interfaces, 9 endpoint constants
```

检查三个方向：后端有而前端缺、前端有而后端无、后端必填而前端标了可选。最后一条最容易出事——它会让运行时拿到 `undefined`。

### 2.3 校验过程中发现并修复的真实问题

| 问题 | 现象 | 修复 |
|---|---|---|
| httpx 默认继承 `HTTP_PROXY` | 本机设了代理，PA 调 NexusPilot（甚至 `127.0.0.1`）被代理拦截，全部 404 | `NexusPilotClient` 增加 `trust_env=False`。这不是测试问题：生产环境导出代理变量会把应用凭据和用户请求送去未知代理 |
| `status` 是自由字符串 | OpenAPI 里是 `string`，前端无法穷举，只能 `as` 断言 | 后端改为 `Literal[...]`，OpenAPI 输出枚举 |
| 错误检查用子串匹配 | `external_user_id` 含 `user_id`，误报"身份外泄" | 改为解析 JSON 后按精确键判断 |

## 4. 字段级协商决议

| # | 议题 | 前端现状 | 后端现状 | 决议 |
|---|---|---|---|---|
| 1 | 时间 | 展示文本 `'10月24日'`、`'明天15:00'` | ISO-8601 + 时区 | 传输一律 ISO-8601 带偏移；展示文本由前端用 `Intl` 生成，不入库、不回传 |
| 2 | 金额 | 字符串 `'89'`、`'129'` | `Decimal(12,2)` | JSON 用两位小数字符串 `"89.00"`；`¥` 和千分位由前端加；禁止 float |
| 3 | 状态 | 中文 `进行中/已完成/全部` | `open/done/archive` 与 `pending/running/...` 两套 | 传输只用小写枚举；中文标签放前端映射表，服务端不返回中文状态 |
| 4 | ID | 字面量 `'demo-lamp'`、`'cinema'` | UUIDv4 | 服务端生成 36 位 UUID；前端示例常量只作 mock，不进入请求 |
| 5 | 去重 | `processedSources` 数组（内存） | 无 | 前端生成稳定 `client_key`（来源 id + 内容哈希），服务端 `(user_id, client_key)` 唯一；重复返回原事务，不新建 |
| 6 | 幂等 | 无概念 | 要求 8–128 字符 | 提交时生成一次，重试复用；切换页面不重新生成 |
| 7 | 分页 | 无（全量渲染） | 签名 cursor | 用 cursor，不用 offset；首页 `limit=20` |
| 8 | 错误 | 无（本地规则） | `{error:{code,message,retryable}}` | 前端按 `code` 分支，`message` 只展示；不得用文案判断类型 |
| 9 | 空值 | `undefined` 居多 | 可空字段显式 `null` | 后端显式返回 `null`，不省略键；前端用 `=== null` 判断 |
| 10 | 排序 | 数组插入顺序 | 未定义 | 时间线按 `occurred_at DESC, id DESC`；同秒不抖动 |
| 11 | 原文 | 存在 `sourceText` 常量 | 无 | 原文单独存 `evidence`，事务只存引用；列表不返回全文，详情按需取 |

## 5. 待建资源与端点（提案，需确认后实施）

### 5.1 四个新资源

```text
matters           事务（电影/退款/心愿/项目/订单/待整理）
captures          交入材料（原文、渠道、去重键、匹配状态）
evidence          原始依据（票据、回执、通知、口述）
matter_actions    事务动作日志（确认关联/撤销/重应用/采纳时间/勾选联系）
```

把 V3 的产品硬规则落成数据结构，而不是靠代码里的 if：

| 产品规则 | 结构约束 |
|---|---|
| 同一来源去重 | `captures(user_id, client_key)` 唯一 |
| 商家已发起 ≠ 到账 | `matters.refund_stage ∈ {requested, merchant_initiated, received}`；`status` 与 `refund_stage` 分离 |
| 金额相同不能自动关联 | `captures.state='needs_confirmation'` + `candidates_json`，必须有一次显式动作 |
| 撤销后同材料不自动重应用 | `matter_actions` 追加式；`captures.state='undone'` 后重放需新动作 |
| 乱序不倒退 | 状态机只允许前进；旧进度事件不覆盖 `received` |
| 未知不猜 | `matters.kind='unknown'`, `status='open'`，不写金额与时间 |

> 2026-10-23 追加：本节的 `matter_actions` 与 `refund_stage` 口径已被 `08-数据库表设计.md` §4 修订——
> 事件表改为 `matter_events`（记录 AI 判断与用户动作），`refund_stage` 明确为由事件归约出的投影字段。
> 本节保留为当时结论，确认后再同步。

### 5.2 八个端点（G1 批次）

| 方法 | 路径 | 用途 | 页面 |
|---|---|---|---|
| GET | `/api/v1/bootstrap` | 我 + 计数 + 今天首屏 | 今天、我的 |
| GET | `/api/v1/matters?filter=&cursor=` | 事务列表 | 事务页 |
| GET | `/api/v1/matters/{id}` | 详情 + 依据 + 可用动作 | 8 个详情页 |
| POST | `/api/v1/matters/{id}/actions` | 统一动作：确认关联/撤销/重应用/采纳时间/勾选联系 | ambiguity、refund、wishPlan、travel |
| POST | `/api/v1/captures` | 交入，返回去重结果与所属事务 | capture、captureSource |
| GET | `/api/v1/captures/{id}` | 匹配依据 | captureSource |
| GET/PATCH | `/api/v1/preferences` | 原文保留、通知偏好 | privacy、我的 |
| GET/PATCH | `/api/v1/memories[/{id}]` | 代理 NexusPilot 记忆 | memories、memory、lesson |

前 7 个由 PA 自己拥有；第 8 个是代理，正文仍在 NexusPilot，需要在 NexusPilot 侧新增 `/api/v1/app/memories` 的 GET/PATCH（现有 `PATCH /memories/{id}` 属浏览器 OWNED 路由，应用令牌用不了）。

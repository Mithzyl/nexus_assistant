# 08 数据库表设计：现状、缺口、JSON 与字段的分工

数据来源：`services/assistant-api/src/assistant_api/models/*.py`。不是照模型文件手抄，而是用同一份
metadata 在内存库执行 `create_all` 导出 DDL，再逐列核对。导出时间 2026-10-23。

现状一句话：**10 张表，只有桥接那 2 张是验证过的；业务那 4 张是脚手架，没有端点在用，也没有迁移。**

## 1. 总览

| 组 | 表 | 写入方 | 状态 |
|---|---|---|---|
| 身份 4 张 | `users` `user_profiles` `user_sessions` `nexus_identity_links` | 本服务 | 登录链路在用，有测试覆盖 |
| 桥接 2 张 | `nexus_runs` `tool_call_receipts` | 本服务 | 真实 HTTP 15 项校验覆盖 |
| 业务 4 张 | `tasks` `schedules` `notes` `business_records` | 本服务 | 仅种子脚本写入，3 个只读工具读取，无端点 |

当前使用 SQLite + SQLAlchemy/aiosqlite。空库和既有库迁移入口为
`scripts/migrate_sqlite.py`（`init` / `upgrade` / `status`）。`create_all` 只用于空库/缺失表
基线；既有表的增量列由迁移器先用 `PRAGMA table_info` 检查后添加。

所有表共用 `TimestampMixin`：`created_at`、`updated_at` 均为 `DATETIME NOT NULL`，由 ORM 写入，没有数据库默认值。

## 3. 现状的六个缺口

### 3.1 没有迁移

`create_all` 只负责"表不存在时建出来"。加字段、改类型、加约束，在已有库上都是静默跳过。
现在之所以没出事，是因为还没有真实数据。G1 加表之前必须先上 Alembic，否则第一次改表就等于要求删库。

### 3.2 业务表与 V3 概念不对应

- `tasks` 只有标题、状态、截止时间：没有商家、金额、来源、退款阶段，"退款待办"放不进去。
- `business_records` 有 `amount`，但没有去重键、没有所属事务，同一张截图交两次就是两笔。
- `notes` 是笔记，不是记忆；记忆正文不在这个库里（在 NexusPilot 的 `llm_memories`）。
- 没有一张表能表达"这件事的依据是哪条原文"。

### 3.3 JSON 列全是裸 JSON

`preferences_json`、`payload_json`、`result_json`、`response_json`、`tags_json` 都没有结构校验。
写错键名不会在写入时报错，只会在某个页面读出 `undefined`。要么在模型层加 Pydantic 校验，
要么在文档里把 schema 固定下来。

### 3.4 状态没有数据库约束

`tasks.status`、`schedules.status`、`nexus_runs.status`、`kind` 都是 `VARCHAR(16)`/`VARCHAR(32)`，
没有 `CHECK`。API 层已经把 Run 状态收成 `Literal`，但裸 SQL 或别的进程写入仍然可以写进任意字符串。

### 3.5 默认值只在应用层

DDL 里没有任何 `DEFAULT`。`default='open'`、`default='CNY'` 都是 ORM 插入时补的。
一旦有第二个写入方（迁移脚本、后台任务、别的服务），漏字段就会变成 NOT NULL 失败或空值。

### 3.6 金额与时间在 SQLite 上的两个坑

- **金额**：SQLite 没有 `DECIMAL`，`NUMERIC(12,2)` 会按 REAL 存。单笔 89.00 看不出问题，
  一旦求和或做 0.1+0.2 类比较就会漂。要么存整数分（`amount_cents INTEGER`），
  要么存两位小数字符串（`TEXT`）。这也正好对上契约里"JSON 传两位小数字符串"的决议。
- **时间**：SQLite 不保留时区，`DateTime(timezone=True)` 取回来是 naive。已有 `as_utc()` 兜底，
  但任何直接比较都必须经过它。

## 4. 退款状态：JSON 还是字段

你的判断对一半：**原文和"AI 读出了什么"必须是 JSON；但"是否到账"不能只存在于 JSON 里等模型每次去读。**
这两件事不冲突，前提是把三层分开。

### 4.1 三层

| 层 | 存什么 | 谁写 | 可改性 |
|---|---|---|---|
| 事实 | 交入原文、渠道、抓取时间 | 用户 / 系统 | 只追加 |
| 判断 | AI 读出的 `refund_stage`、依据片段、置信度、模型与提示词版本 | AI | 只追加，不覆盖 |
| 投影 | `matters.refund_stage`、待办计数、"下一步" | 归约函数 | 可重建，任何人不手改 |

字段不是第二个真相，它是 JSON 的**物化结果**。规则是：删掉投影列，能用事件重算出一样的值。

### 4.2 为什么不能只有 JSON

- **列表要能查**：今天几笔待退款、按时间排序、按阶段筛选。JSON 全表扫，MySQL 上做表达式索引更麻烦。
- **数字不能随模型漂**：如果每次都由模型读 JSON 现判，模型或提示词一升级，同一批数据可能昨天是 3 笔、今天是 4 笔。
- **争议要能回答"依据哪条、谁在什么时候改的"**：JSON 原地覆盖就丢了这段历史。
- **硬规则要结构约束**："商家已发起 ≠ 到账"如果只写在提示词里，等于靠模型自觉；写成约束才拦得住。

### 4.3 为什么也不能只有字段

- 商家话术写不全，提前归一化会丢证据（"已为您提交退款申请，预计 1–3 个工作日到账"到底算哪个阶段？）。
- "未知不猜"要求没有把握时字段是 `null`，而原文必须原样保留——只有 JSON 放得下。
- AI 需要参考的正是原文，不是被压扁的枚举。

### 4.4 落法：事件 + 归约

```text
matter_events  (append-only，唯一真相)
  event_id, matter_id, user_id, kind, source, occurred_at, received_at,
  actor,               -- user | ai | system
  payload_json,        -- 原文或结构化观察，不裁剪
  interpretation_json  -- AI 的判断：{refund_stage, confidence, evidence_span}

matters.refund_stage   -- = reduce(matter_events)，纯函数，可 rebuild
```

归约三条规则，全部可测：

1. 只前进：`requested → merchant_initiated → received`，`received` 是终态。
2. 乱序不倒退：`occurred_at` 早于当前阶段最后变更时间的事件，只入库、不改投影。
3. AI 只能追加 `interpretation_json`；改投影的只有归约函数，没有"AI 直接 UPDATE 状态"这条路。

这样同时满足两件事：AI 拿到的是完整 JSON（原文 + 它自己的判断 + 置信度），页面拿到的是可查询的字段，
字段还能随时从事件重建。代价是多一层归约函数和一张会长大的事件表，需要一条 `rebuild` 命令来证明它真的可重算。

`refund_stage` 是目前**唯一**带业务语义的投影。这不是因为"业务只有这几种"，而是因为 V3 有一条硬规则
要求它必须被强制（商家已发起 ≠ 到账）。其余业务内容不建列，见 §5.1。

### 5.1 投影不是业务字段清单

未来会有保修期、疫苗到期、快递滞留、房租押金、签证有效期……不可能预先把它们都建成列。
所以投影只回答一个问题：**当前 UI 和规则要对哪些键排序、筛选、计数、触发提醒。**

`matters` 里真正参与查询的只有七个：`kind`、`status`、`occurred_at`、`due_at`、`amount_cents`、
`currency`、`refund_stage`。其余全部在 `detail_json`，包括每种事务自己的字段：

```json
{
  "merchant": "某某眼镜店",
  "items": [{"name": "镜片", "amount_cents": 8900}],
  "warranty_until": "2027-10-22",
  "refund": {"channel": "wechat", "expected_days": 3}
}
```

新增一种事务类型时，**只改 `detail_json` 的 schema，不改表结构**。

**什么时候才升成列**：只有出现 `ORDER BY` / `WHERE` / `COUNT` / 定时触发这四种需求，且数据量证明
JSON 表达式查询不够快。升级分三步，每一步都不用搬数据：

1. 先用 JSON 表达式查（SQLite `json_extract`，MySQL `detail_json->>'$.key'`）。
2. 慢了加生成列 + 索引（MySQL `GENERATED ALWAYS AS (...)`，SQLite 表达式索引），读写代码不改。
3. 还需要跨行约束（唯一性、状态机），才升真列，从 `detail_json` 回填一次。

反例是每来一种事务就 `ALTER TABLE`：SQLite 改表要重建整张表，MySQL 上表会宽到几十列、大半是 null，
索引跟着膨胀。JSON 不是过渡方案，它就是开放式内容的正解；字段只是它的索引。

本机 SQLite 已用三条假数据验证过（退款 / 保修 / 签证三种 kind 共用一张表）：表结构未改，三种记录都能写入；
按 `json_extract(detail_json,'$.warranty_until')` 过滤能命中断言式索引（`SEARCH matters USING INDEX`）；
写 `refund_stage='arrived'` 被 `CHECK` 拒绝。MySQL 上未验证。

**AI 那条路不受投影限制。** 模型读的是 `detail_json` 和原文，不是读列。但也不能整包塞，按三层取：

| 场景 | 取什么 | 量级 |
|---|---|---|
| 列表、检索、去重 | `title` + `kind` + `occurred_at` | 几十字节 |
| 回答、整理 | 相关事务的 `detail_json` | 几百字节 |
| 追问依据 | `evidence` 指向的原文片段 | 按需 |

一次 run 只带相关事务，不把用户全部 JSON 塞进上下文——那既烧 token，也会让"未知不猜"失效（材料越多，模型越容易自己补）。

与 07 文档 §5.1 的差异（07 保留为历史，待确认后同步）：

- `matter_actions` → `matter_events`：不只记用户动作，也记 AI 判断，并用 `actor` 区分。
- `evidence` 明确为"事务 ↔ 交入材料"的引用表，原文只在 `captures` 存一份。
- `refund_stage` 明确为投影字段，不是可手改的状态。

旧的 4 张业务表**保持不动**：`list_user_tasks`、`search_user_notes`、`get_calendar_events`
三个工具还在读它们，G1 只加不删。要合并，得同批改工具并重跑工具回放测试。

## 6. 未验证的部分

- §5.1 的三种 kind 共存与表达式索引只在内存 SQLite 上用假数据验证过，MySQL 8.4 的 JSON 路径索引未验证。

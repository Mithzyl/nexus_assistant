### 7.3 客户端读取顺序

- 聊天：`POST /asks` 得 `local_run_id` → 列表/详情读同一 id → 事件用 SSE → 刷新走详情；
  内部运行不会出现在列表，猜中 id 也会得到 404。
- 通勤：`POST checks` 得 `check_id`（202 仅表示受理）→ 轮询 `GET /checks/{id}` 的
  `status/phase/phase_updated_at` → 终态后用 `advisory_id` 读 `GET /advisories/{id}`，
  不要用 latest 代替本次结果 → 天气单独读 `/weather`。
- 三个时间信号：`server_time`（服务器能否响应）、`worker/scheduler.last_seen_at`
  （后台是否报到）、`phase_updated_at`（任务是否推进）；不要互相替代。
- 旧缓存：`POST /asks/verify` 只清理 `not_chat`；`unknown` 保留重试；
  404 和“不在最近一页”都不是删除依据。

### 10.5 本轮验证（脚本已验证；共同服务未启动）

| 场景 | 结果 |
|---|---|
| 初始化 | 新建库并记录 0001–0006 迁移；合成账号 `dev-a@example.com` + 示例数据 |

| 心跳变旧 | 把 `last_seen_at` 设为 120 秒前：`worker/scheduler` 均为 `stale` |
| 无心跳行 | 删除心跳行后：`not_seen`，排队任务仍如实等待 |

| 备份 | 在线备份成功，`integrity ok`，计数与迁移完整 |
| 副本恢复 | `restore-check`：计数一致、样本 ID 一致（同一批测试记录） |
| 停止安全性 | 伪造一个不属于本脚本的 PID：`stop` 拒绝并保持该进程存活 |
| 未跟踪进程 | 心跳仍新鲜但没有 PID 记录时，`doctor`/`start` 会告警或拒绝；`stop` 不会按名字杀进程 |

已知机制限制（实测）：一次性 worker 退出后，它的心跳在 60 秒阈值内仍可能显示
`online`；这是现有设计，不是“进程仍在运行”的证明。

验证中发现并已处理的缺口：一次停止安全测试把 `data/run/worker.json` 临时替换成
诱饵 PID，导致真实 worker 失去 PID 记录并继续运行；核对 `pgrep` 后已手动停止。
脚本现在会检测“心跳仍新鲜但没有本脚本 PID 记录”和“端口被占用但无记录”，
分别告警或拒绝启动，并且仍然不会按名字杀死进程。

### 10.6 客户端怎么读后台状态

- `server_time`：本次响应时间，只表示“服务器能回应”。
- `worker.last_seen_at`：执行程序最近一次报到时间。
- `worker.state`：`online`（阈值内报到，默认 60s）、`stale`（超过阈值）、
  `not_seen`（当前库没有心跳行，可能从未启动或连了另一份库）。
  `online` 不保证进程此刻仍活着。
- `latest_check.phase_updated_at` / `last_progress_at`：任务最近推进时间，不是进程心跳。
- `latest_check` 只是本账号最近创建的一条检查，**不是**用户当前打开的那一条；
  当前任务进度看该 `check_id` 的 `GET /api/v1/checks/{id}`。
- 任务等待、处理、完成、失败分别看 `status`；正在做什么看 `phase`，没有假百分比。

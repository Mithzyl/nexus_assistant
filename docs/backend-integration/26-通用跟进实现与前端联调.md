# 通用跟进实现与前端联调

## 1. 交付范围

本批在 backend worktree 实现 P0：引用原业务记录、共用 AI 接口调用、时间与记录变化触发、暂停和结束、后台问题续问、结果卡片及执行恢复。前端未修改。

Assistant 从运行中的 OpenAPI 检索接口，Nexus 返回操作和参数，Assistant 调用原业务路由。新增业务不需要加入工具执行字典。通勤计划、天气、路线、日程等接口在同一目录内；每天的通勤 AI 跟进由通用规则执行。

用户明确输入要求后直接处理。用户需要决定具体安排时，使用现有 ask_user 交互。回答简短自然，卡片展示实际安排；没有新变化时保持安静。

本批不增加地图内容块、复杂方案选项、通用周期表达式或新的外部通知渠道。现有图片、时间线等卡片能力继续使用。

## 2. 后端运行与迁移

在 backend worktree 的 `services/assistant-api` 目录：

```bash
.venv/bin/pip install -e '.[dev]'
.venv/bin/python -m scripts.migrate_sqlite upgrade
.venv/bin/python -m uvicorn assistant_api.main:app --port 8010
.venv/bin/python -m assistant_api.background scheduler
.venv/bin/python -m assistant_api.background worker
```

空库使用 `scripts.migrate_sqlite init`。新增版本 `0021_follow_ups` 创建 `follow_ups`、`follow_up_executions`、`business_change_events`；保留原事项、待办和日程表及记录。

API、scheduler、worker 使用同一配置和 SQLite。两个后台入口支持 `--once`。`scripts/dev_env.py start` 已改为启动通用入口，原开发环境启动前检查增加了新表与迁移版本。

通用 scheduler 根据到期时间和已提交的记录变化处理规则。通用 worker 使用共用执行上下文调用接口。现有通勤供应商检查和通知队列仍由同一 worker 消费；它们属于业务接口的计算、发送实现，不再作为唯一的后台入口。自动通勤 AI 使用通用跟进流程；原天气定时刷新保留为非 AI 的供应商工作。

已保存通勤计划在启用 `ASSISTANT_COMMUTE_AUTO_AI_ENABLED=true` 后，按计划时区、星期、生效日期和检查时间生成每日跟进；已过当天到达时间不补发当天任务。计划修改后原版本的跟进结束，使用新版本安排。没有关联事项的旧计划会关联本地创建的通勤事项。原有计划 ID 保留。

本次没有对实际业务库执行迁移，没有替换用户正在运行的服务。上述命令供加载本分支时使用。

## 4. 用户输入与续问

```json
{
  "text": "合同收到了",
  "idempotency_key": "web-input-example-002",
  "continuation_run_id": "上一条问题的local_run_id",
  "memory_disclosures": []
}
```

| 字段 | 类型与要求 |
|---|---|
| `text` | 必填字符串，1～4000 字符 |
| `idempotency_key` | 必填字符串，8～128 字符；同次网络重试复用，新输入生成新值 |
| `continuation_run_id` | 可省略或 null；回答后台或聊天问题时，传原问题的 local_run_id |
| `memory_disclosures` | 当前通用调用流程省略或传空数组 |

同一键不会重新执行已保存操作。读取历史、结果详情不会发起业务写入。

后台问题与聊天问题的回答方式相同：用户点选 choices 或自由输入，使用新的 idempotency_key，传原 local_run_id。后端将结果关联回原跟进执行。前端不需要另一套“执行方案”接口。

## 5. 提问和历史结果新增字段

沿用现有 `outcome / answer / clarify / pending_context / local_run_id / parent_run_id`，新增：

```ts
type IntakeSource = 'chat' | 'follow_up';
interface IntakeOrigin {
  source: IntakeSource;
  matter_id: string | null;
  follow_up_id: string | null;
  follow_up_execution_id: string | null;
}
```

- `source=chat`：用户输入形成的消息，保留用户输入气泡。
- `source=follow_up`：后台产生的助手消息，直接展示助手回答或问题；不要将内部 instruction 展示成用户发送的气泡。
- `matter_id`：可用于打开对应事项。
- `follow_up_id`：可读取跟进详情。
- `follow_up_execution_id`：关联本次处理；普通页面不需要展示编号。

历史接口同样返回这些来源字段。旧记录默认 source=chat，关联字段可以为空。

```json
{
  "source": "follow_up",
  "matter_id": "事项ID",
  "follow_up_id": "跟进ID",
  "follow_up_execution_id": "执行ID",
  "local_run_id": "问题对应的RunID",
  "parent_run_id": null,
  "intent": "question",
  "outcome": "needs_clarification",
  "answer": null,
  "clarify": "合同修订版收到了吗？",
  "pending_context": { "choices": ["收到了", "还没有"] }
}
```

`outcome` 沿用 answer、needs_clarification、processing、unknown、failed、cancelled，以及旧 draft。`answer` 表示本轮回答结束；卡片使用自己的状态表达对应结果。运行记录的 status 不作为业务操作成功的唯一依据。

## 6. 流式事件

POST 请求体与普通输入一致，Accept 为 `text/event-stream`。

| 事件 | 数据 | 前端处理 |
|---|---|---|
| accepted | `{}` | 显示正在处理 |
| answer | `{ "text": "累计回答全文" }` | 替换当前流式正文，不重复追加累计全文 |
| result | 完整提问响应 | 使用最终 answer、clarify、cards 及来源字段 |
| error | 现有结构化错误结果 | 沿用当前请求错误交互，保留原输入 |

心跳是 SSE 注释帧。卡片在最终 result 中一次性返回。内部调用 JSON 不进入回答流。网络中断后查询原结果，复用原请求标识；不能因没有收到最终帧而新增一次修改。

没有正文、问题或卡片的结果不生成可见气泡。后台消息不依赖用户正在连接的 SSE；通过现有历史和事项接口读取。页面重新获得焦点或刷新时读取最新消息即可，第一版不新增长期推送连接。

## 7. 通用卡片

仍通过 `pending_context.cards` 返回。模型引用由后端解析，浏览器收到普通值：

```ts
interface EmbeddedCard {
  kind: 'result' | 'plan' | 'info';
  title: string;
  subtitle?: string;
  status: 'completed' | 'failed' | 'unknown' | 'suggestion' | 'info';
  blocks: ResponseBlock[];
}
type ResponseBlock =
  | { type: 'text'; text: string }
  | { type: 'fields'; items: ResponseField[] }
  | ({ type: 'image' } & ResponseImage)
  | { type: 'timeline'; items: ResponseTimelineItem[] };
interface ResponseField {
  label: string;
  value: string | number | boolean | null;
  format?: 'text' | 'datetime' | 'date' | 'time' | 'number';
}
interface ResponseImage { src: string; alt: string; caption?: string }
interface ResponseTimelineItem {
  title: string; subtitle?: string; time?: string; description?: string;
  category?: string; image?: ResponseImage; fields?: ResponseField[];
  link?: { label: string; href: string }; connector?: string;
}
```

最多 6 张卡片，每张 12 块；字段块 24 项；时间线 30 项。`connector` 属于从上一站到当前站的衔接，放在第二站起的节点上。图片支持 HTTPS 或本站路径。

result 的状态由实际回执生成；plan 固定为 suggestion，info 固定为 info。前端按 type 渲染，按后端状态展示，不按业务名称增加卡片注册。

```json
{
  "answer": "改好了，面谈改到十二点。",
  "outcome": "answer",
  "pending_context": {
    "cards": [{
      "kind": "result", "title": "面谈安排", "status": "completed",
      "blocks": [{
        "type": "fields",
        "items": [
          {"label": "时间", "value": "2030-01-03T12:00:00Z", "format": "datetime"},
          {"label": "地点", "value": "会议室", "format": "text"}
        ]
      }]
    }]
  }
}
```

`pending_context.execution_result` 保留原回执兼容展示。优先显示 cards；没有 cards 时才使用旧回执展示，避免重复。

## 8. 跟进规则接口字段

创建示例，所有 ID 均为结构占位，实际从所属账号接口结果取得：

```json
{
  "idempotency_key": "followup-create-example-001",
  "matter_id": "所属事项ID",
  "title": "跟进合同修订版",
  "instruction": "合同未收到时问我是否收到。",
  "references": [{
    "name": "contract",
    "operation_id": "get_matter_api_v1_matters__matter_id__get",
    "path_parameters": {"matter_id": "所属事项ID"},
    "query_parameters": {},
    "result_pointer": "/todos",
    "match": {"todo_id": "原合同待办ID"}
  }],
  "trigger": {
    "kind": "time",
    "source": {"reference": "contract", "field": "/due_at"},
    "offset_seconds": 0
  },
  "stop_when": [{
    "reference": "contract", "field": "/status", "operator": "eq", "value": "done"
  }]
}
```

| 字段 | 说明 |
|---|---|
| matter_id | 必填，所属事项 |
| title | 必填，1～180 字符，用户可理解的跟进名称 |
| instruction | 必填，1～2000 字符，触发后处理什么 |
| execution_mode | evaluate（默认）：检查与提示；execute：按用户保存的要求执行修改。由 Assistant 根据任务填写，页面无需新增配置项 |
| references | 必填，1～12 个记录引用；不复制业务正文 |
| trigger | 必填，时间或记录变化触发 |
| stop_when | 默认空数组，最多 12 个；任意一项成立即结束该跟进 |
| idempotency_key | 必填，8～128 字符 |

引用字段：name 为本条规则内唯一名称；operation_id 为运行中 OpenAPI 的 GET 操作；path_parameters/query_parameters 默认空对象。result_pointer 默认根对象空字符串。查询返回集合时，match 使用字段和值唯一选择其中一条记录。

时间触发任选一种：

```json
{"kind":"time","at":"2030-01-02T10:00:00+08:00"}
```

```json
{"kind":"time","source":{"reference":"contract","field":"/due_at"},"offset_seconds":0}
```

时间字段变化后，后端更新 next_trigger_at，并取消旧时间对应的待执行任务。

记录变化触发：

```json
{"kind":"record_changed","reference":"meeting","fields":["/starts_at","/location"]}
```

fields 最多 12 项。字段路径使用 JSON Pointer。停止条件 operator 支持 eq、ne，value 为字符串、整数、布尔或 null。

创建成功返回 HTTP 201 和 FollowUpRead：

```ts
interface FollowUpRead {
  follow_up_id: string; matter_id: string; title: string; instruction: string;
  state: 'enabled' | 'paused' | 'closed'; version: number; execution_mode: 'evaluate' | 'execute';
  references: RecordReference[]; trigger: FollowUpTrigger;
  stop_when: StopCondition[]; next_trigger_at: string | null;
  created_at: string; updated_at: string;
}
```

返回的 references、trigger、stop_when 与上述参数结构一致，默认字段可能补齐。状态由后端返回，页面不根据时间自行完成事项。

GET 列表支持 matter_id、state、limit；state 可选 enabled/paused/closed，limit 默认 20，范围 1～100。页面通常按事项读取 enabled 跟进；需要暂停记录时再查询 paused。

PATCH 示例：

```json
{"expected_version": 3, "state": "paused"}
```

恢复使用 state=enabled，结束使用 state=closed。也可修改 title、instruction、execution_mode、references、trigger、stop_when，省略的字段保持原值。使用最近读取的 version 作为 expected_version。暂停时，尚未执行及等待用户的任务停止，运行中的任务不再开始后续调用或发布旧结果。

## 9. 跟进处理记录

GET executions 的 limit 默认 20，范围 1～50，按创建时间倒序：

```json
[{
  "execution_id": "执行ID",
  "follow_up_id": "跟进ID",
  "state": "waiting_user",
  "local_run_id": "问题对应的RunID",
  "created_at": "2030-01-02T10:00:00Z"
}]
```

执行状态为 queued/running/waiting_user/succeeded/failed/unknown/skipped。通过 local_run_id 读取现有 intake 结果，取得正文、卡片或问题；处理记录编号和运行阶段无需组成产品状态卡。

事项的 active/waiting/archived/deleted 生命周期继续由原事项接口维护。暂停跟进不会自动归档事项；事项暂停或归档后，相关跟进停止。

## 10. 后端内部调用与恢复

接口校验与执行在 `services/api_operations.py`；共用调用循环在 `services/operation_intake.py`；规则与执行在 `services/follow_ups.py`；后台入口是 `assistant_api.background`。

每个 HTTP 操作前保存执行意图和步骤认领，操作后保存实际回执。结果按步骤保存，AI 参数或卡片可使用 `{"$result":"/字段路径","step":0}` 引用对应实际步骤，浏览器不处理引用表达式。

进程在保存回执后停止，恢复会从后续步骤继续。已经发出但没有保存回执的调用保留待查询结果，不自动再次发送。规则变化、暂停、所属事项停止会在下一步调用前检查。

业务 ORM 修改和批量 SQL 更新在原事务内保存必要的变化事件。后台读取关联记录最新值，不复制整份日程、待办。变化由本条执行引起时，不循环触发自己。

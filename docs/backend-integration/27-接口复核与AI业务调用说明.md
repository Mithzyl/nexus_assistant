## 当前一级索引协议（2026-11-09）

Assistant不解释用户的否定语义，不按用户任务预选八份完整业务定义。首轮提供`operation_index`（每页最多128项，每项仅含uri、summary和effect，另有total及next_offset），只预加载`resolve_operation_definitions`。Nexus选择uri，按`decision=call`调用解析工具；Assistant经原认证路由`POST /api/v1/operation-catalog/resolve`返回完整api_operations及共享components.schemas，Nexus再决定是否执行业务、继续获取定义或终答/追问。方法、路径和完整字段在解析结果中提供，不在一级目录重复；一次最多8个uri只限制单次响应体积。

`decision=search`按模型给出的关键词查简短目录，或以空查询和search_offset翻页，不自动提供完整参数。已获取定义在原Agent中继续使用，重复解析不再次追加定义和共享结构。未加载定义的业务操作返回operation_definition_required；无效uri在读取前拒绝，不当成外部URL访问。现有运行已提供的业务定义继续有效，不切换或重建Agent。用户身份、权限、版本、完整调用参数/summary/实际结果和未知写入停止规则均保留。

后续按需规则：初始消息已经携带索引，不强制search或解析；普通问答直接answer，需求不明先ask_user。只有第一次使用尚未加载完整定义的业务接口才解析，可一次取多个；同Agent直接复用，新增能力只取新增定义，参数错误只修正参数。当前Run初始消息及成功回调的实际返回是定义已提供的依据，其他Agent记录或缓存标记不算。新Agent重置加载标记；当前发布结构发生变化时，业务调用在执行前返回operation_definition_stale，新返回的对应定义和共享结构替代旧说明。结构比较不使用哈希；只读解析工具按当前请求参数校验，避免共享错误结构变化阻塞重载。

这些后续规则通过`tests/test_operation_index.py`的12项隔离数据库回调检查，不重复调用模型；包含普通回答/追问零解析、同Agent多次调用及参数修正、新Agent缓存隔离、无消息定义的缓存标记拒绝，以及定义/共享结构变化后重取。下方消耗对比属于此前版本；11 月 10 日另有按需定义与联合业务真实场景，见 05，不等于全部边界情况和复杂任务均已重验。

## 单 Agent 正文处理接入（2026-11-05）

**状态：进行中，工作区已实现并通过限定隔离联合验证，未部署。** Nexus 对应实现为 `fce2c8f`、`754ddbe`；Assistant 对应当前 `backend/dev` 工作区，不能仅用其旧 HEAD `5ce0b38` 表示本次新代码。

### 正式入口与结果

1. Assistant 保存原用户输入和业务关联，创建一次 `/api/v1/app/runs` 及该 Run 的 `agent-workflows`。后续 GET、SSE 重连和同请求复用原编号。
2. 工作流配置采用 `application_response_mode=caller_processed`、`application_protocol_instructions` 和 `final_output_schema`。普通 Nexus 对话不启用本模式。
3. Nexus 将完整模型正文发送到服务端已绑定的 `POST /internal/nexus/agent-responses`。信封字段为 `protocol_version=1`、`application_id`、`external_user_id`、`run_id`、`workflow_id`、`response_id`、`execution_id` 和原始 `content`。认证使用独立服务端 Bearer 凭据，地址与身份不能来自模型。
4. Assistant 解析 `decision: call`，用 `OperationCatalog.validate_call()` 校验发布接口和参数，再由 `execute_call()` 经过原认证与业务路由执行。不会执行模型提供的 URL、命令或函数代码。模型原文、完整提议和 `summary` 保留；实际业务请求键由服务端绑定。
5. Nexus 等待 HTTP 结果，以 `execution_id` 关联原模型正文，将正文及标记为后端事实的结果追加到原消息序列。结果包含原业务状态、必要实际字段、`executed_call`、`executed_arguments` 和 `proposed_summary`，不再只有 `result_shape`。不重建另一套规划请求。
6. 模型自主终答或追问，平台确认 `complete` 后 Nexus 继续执行最终结构与既定审核检查。Assistant 只在 Nexus 成功结束后投影为现有 `outcome + answer + pending_context.cards`，不将中间 JSON 当作用户正文；页面仍要求 answer 非空。

平台返回固定外层：`protocol_version`、`execution_id`、`disposition`。`complete` 仅包含这三项；其他结果另含 `execution_status`、`result` 和 `error`。

| 平台结果 | 处理要求 |
| --- | --- |
| continue / succeeded | 返回实际业务结果，由原 Agent 判断下一步；成功执行不等于用户目标已经全部完成 |
| continue / failed | 当前参数检查未产生写入时可以修正；是否继续以 retryable 和运行状态为准 |
| continue / rejected | 权限、状态或重复业务提议被拒绝；不通过换参数或编号绕过 |
| stop / unknown | 可能已经写入或处理结果不明，停止自动执行，不盲目重试 |
| complete | 认可当前正文为候选终答，不替换其内容，也不绕过 Nexus 最终检查 |

相同 execution_id 和相同请求返回原回执，不同请求冲突；相同任务下已成功的语义重复写入被拒绝。`AgentResponseReceipt` 与运行内处理标记在发出业务操作前持久保存；中断留下 dispatching 状态时按未知处理。具体实现见 `services/agent_responses.py`，模型参数从不决定可信用户。

## AI 获得的调用要求从哪里来

真实 HTTP 路由与 Pydantic 请求/响应类型是接口定义来源。Assistant 从 app.openapi() 建目录，按当前输入和允许的历史检索；Nexus 只得到被选接口及必要结构，不扫描代码，也不维护 Assistant 的业务目录。

业务接口继续使用已有认证、所有权、状态、版本和保存函数。新接口只需要正常发布 OpenAPI，通用执行器不增加 Python handler 字典条目。多步业务在对应路由发布步骤说明，不把接口到执行函数的另一份映射写进规划器。

| 路由 OpenAPI 字段 | 用途 |
| --- | --- |
| operationId | 调用标识，必须唯一，由当前 FastAPI 生成或显式指定 |
| summary / description | 检索用途、前提、字段含义、效果及下一步要求 |
| parameters / requestBody | 路径、查询、请求头、JSON 参数及必填、范围和条件 |
| responses | 成功和失败响应结构；引用组件按选中接口收集 |
| x-assistant.enabled | false 时不提供给 AI；reason 说明具体原因 |
| x-assistant.effect | read、preview 或 write；用于区分查询、准备步骤和正式写入 |
| x-assistant.keywords | 可选业务检索词，避免长描述中的反向说明抢占检索结果 |
| x-assistant.next | 可选数组：method、path、purpose；按当前 OpenAPI 解析 operation_id，不注册新执行代码 |
| x-assistant.required_headers | 可选：补充原服务实际要求的请求头。本轮 If-Match 保持原 HTTP 缺省时返回428，目录按必需项校验 |

这些字段是开发及调用说明，不直接呈现在用户卡片。当前目录最多选 8 个相关接口，优先包含最近实际操作声明的下一步；不把整个应用的 OpenAPI 发送给模型。模型仍可能选错接口或参数，实际执行以本地校验及真实响应为准。

1. GET `/matters/{matter_id}`，以用户当前输入及允许历史的条件唯一定位原schedule_id或todo_id。

5. 用真实 ConfirmResponse 或读取事项详情生成卡片；不通过重新创建来代替修改。

### 完整 PUT 与请求头参数

通勤计划 PUT 要求完整可写配置及当前 If-Match。可引用本地GET结果：

```json
{
  "operation_id":"update_commute_plan_api_v1_commute_plans__plan_id__put",
  "path_parameters":{"plan_id":"已查询确认的原plan_id"},
  "headers":{"If-Match":{"$result":"/revision","as":"string"}},
  "body":{
    "$result":"",
    "pick":["name","effective_from","enabled","timezone","weekdays","arrival_local_time","check_local_time","transport_mode","buffer_minutes","rain_probability_threshold","rain_extra_buffer_minutes","notify_enabled","origin","destination"],
    "overrides":{"name":"新通勤"}
  }
}
```

pick仅选择当前响应中真实存在的字段，保留原值；as=string只转换标量，不执行代码。$result可加step引用早先保存的成功响应。where必须唯一匹配，不能按数组位置猜选多条记录。所有引用在本地解析，之后再按目标接口校验。请求头最终必须为字符串，认证信息不能由模型提供。

### 完整通勤安排

`POST /api/v1/matters/commute-drafts`，operation_id=`create_commute_draft`，复用 commute_bundle.create_draft。

输入：idempotency_key、origin_query、destination_query、city、arrival_local_time必填；title默认“日常通勤安排”；effective_from、weekdays、buffer_minutes可暂缺，测算前需明确。weekdays为1–7整数列表，时间为HH:mm。不需要AI伪造坐标。

响应：DraftRead，payload.commute中包含intent、timezone、origin_search、destination_search和真实候选。引用唯一选择的selection_token，调用已有 `/matters/drafts/{draft_id}/commute-quote`，提供expected_version、origin_token、destination_token、effective_from、weekdays、buffer_minutes、mode。普通调用保留test_only=false。测算返回新的草稿版本，再confirm保存完整事项、首日日程和周期计划。后续generate-day要求该计划仍启用、matter_id及first_schedule_id有效、日期在生效周期内且未过目标到达时间。

直接 POST `/commute-plans` 仍然只创建周期配置，不能当作完整通勤安排保存完成。

### 跟进、提醒及状态动作

跟进沿用 create/get/patch/executions：先读取原业务记录，保存只读接口引用与唯一条件；时间触发在at和source中二选一，record_changed需要reference及非空fields。evaluate只检查提示，execute用于用户已明确授权的后续修改。暂停、恢复、结束用当前expected_version，不再次请求确认。

待办完成、恢复，提醒知晓，事项归档、恢复、撤回继续调用原接口；它们的效果不同，description已逐项说明。例如知晓提醒不会完成待办；归档默认取消未来日程，保留时应传cancel_future_schedules=false；是否取消提醒由用户要求决定。

## 提示词与本地执行

`matter_plan.API_PROMPT` 描述中间业务提议、最终回答和卡片规则；`operation_intake.workflow_configuration()` 将协议固定到工作流，`matter_plan` 将当前输入和相关 OpenAPI 结构作为本次输入传递。当前上下文不再使用 Assistant 的 remaining_steps 决定模型何时结束。

AI 可以返回 call、search、ask_user/clarify 或 answer。平台只做业务处理、校验和结果投影；`search` 返回相关接口说明，原 Agent 继续读取，不另建运行。description 与 next_operations 继续描述业务的依赖步骤，preview 不能当作正式保存成功。原目标不唯一时询问具体条件，不额外增加确认按钮。

通用卡片的 `$result` 仍由 Assistant 绑定本次实际回执，避免模型编造业务值。正文、AI 提议与后端事实各自保存；新的正文模式已返回必要业务字段，旧的“正文一律只保留本地、给 AI 只有结构”要求已删除。模型对时区、状态或通知的解释仍需明确证据，不能只凭回答文本认定业务正确。

## 2026-11-09：Assistant 自有记忆工具

记忆与其他业务采用同一正文处理协议：Nexus 读取 Assistant 提供的 OpenAPI 定义，生成 `mutate_business_memory` 或 `recall_business_memory` 的完整参数；Assistant 实际读写自己的数据库并返回结果，原 Agent 继续。无需在 Nexus 注册记忆业务名称或新增静态分支，不使用 Nexus 原生平台记忆工具。首次检索、当场业务依赖与回答后队列的位置和字段统一见 [05](05-Agent-工具-记忆运行流程.md)。`after_answer` 返回 queued 仅代表持久化登记，不能提前声称修改成功；后台只执行已登记参数，不再调用模型。

## 2. 已接入页面能力

### 2.1 结构化日程与待办编辑

- 新增 `POST /matters/{matter_id}/drafts` 调用。请求带稳定幂等标识，并且只提交
  `schedule_id` 或 `todo_id` 其中一个。
- 日程“调整”直接读取服务器日程并生成 `schedule` 预览；待办“时间”直接读取服务器
  待办并生成 `todo` 预览。两条路径不再把表单拼成文字交给事项模型。
- 日程可修改标题、开始、结束和地点；待办可修改标题、截止时间和提醒时间。
- 只调整日程或只调整待办时，草稿按服务器返回的 `source_text` 和 payload 识别为对应
  模式，不展示、不要求也不提交事项标题。
- 清空已有提醒时，面板明确说明确认后会取消对应待发提醒；截止时间与提醒时间分别编辑。
- 苹果端导入的日程保持只读。页面禁用“调整”，服务端仍以
  `schedule_not_editable` 拒绝绕过请求。

### 2.2 草稿和冲突方案

- 草稿面板区分新建事项、修改事项、只调整日程和只调整待办。
- 保存只调用 `PATCH /matters/drafts/{id}` 更新预览；再次点击“确认更新”才调用
  `POST /matters/drafts/{id}/confirm`。
- 新建事项才要求事项标题；修改事项不因标题为空而阻止日程/待办编辑，也不会把空标题
  写入正式事项。
- 现有待办 ID 在保存和确认时原样保留。未修改的截止、提醒和标题不会被清空；只有用户
  明确清空提醒时才提交 `reminder_at: null`。
- 选择 A/B/C 方案后，面板列出服务器预览将改变的内容，包括本次时间、相邻安排和方案
  新增的待办。
- 方案读取服务器返回的 `executable`、`unavailable_reason` 和 `affected`。不可执行方案
  禁用并显示原因；服务端仍以 `option_not_executable` 拒绝直接调用。
- 跨事项 B 方案显示受影响事项、日程及修改前后时间。选择后以服务器返回的完整草稿替换
  页面状态，前端不自行累加时间偏移。
- 切换方案会重新读取服务器结果；手工修改字段会清除旧方案选择和风险确认。
- 冲突计算、方案应用和版本变化全部以服务器返回为准，网页不做本地时间计算来绕过冲突。
- `eta_status=unverified` 即使没有确定时间冲突，也显示“路程尚未核实”，不显示成所有
  风险已排除。
- 草稿可以显式取消。取消成功、确认成功或确认结果冲突后，相关页面重新读取服务器状态。

### 2.3 变更历史与撤回

- 详情页读取 `GET /matters/{matter_id}/changes`，刷新后仍显示时间、修改内容和“已生效”
  状态。
- 不再依赖页面内 `lastChangeId`，也不向页面显示 `change_id`。
- 只有服务器返回 `revertable: true` 的变更显示撤回操作。
- `later_changes`、`already_reverted`、`matter_changed`、`schedule_changed`、
  `todo_changed`、`reminder_changed`、`incomplete_change_snapshot` 等原因转为用户可读
  说明，不显示内部名称。
- `creation_revert_unsupported` 显示“暂不支持撤回新建事项”，不在页面复制内部规划说明。
- 跨事项关联变更显示 `relation=affected`、来源事项标题和入口；当前事项不显示撤回按钮，
  由来源事项处理，不拼接错误的 `matter_id/change_id`。
- 撤回确认框说明会恢复的事项字段、日程时间地点、已完成待办或待发提醒。
- 撤回后重新读取事项详情、变更历史，并通知已挂载的“今天”页重新读取。
- 服务端标记为不可撤回的记录只显示原因，不显示成可安全撤回。

### 2.4 今天页

- 读取 `GET /today` 的 `schedules`、`reminders`、`deadlines`、`drafts`、`changes`。
- 截止事项显示逾期和当天到期的未完成待办，按 `due_at` 排序；不设置规划未确认的
  “临近”阈值。
- 待确认卡片显示所属事项、日程标题、服务器影响说明和需要处理的问题。点击后读取完整
  草稿并打开现有底部确认面板。
- 已确认变更单独放在“已生效变更”折叠区，可进入所属事项的变更历史。
- 日程和提醒显示所属事项标题；提醒只显示一次“尚未确认送达”的统一说明。
- 每条日程显示 `route.status`。路线未核实或不可用时始终显示简短原因，即使没有时间冲突。
- 固定通勤建议继续独立展示，不把最新通勤结果关联到任意一条日程。
- 草稿确认、取消或变更撤回后，今天页通过现有页面刷新入口重新读取，不建立后台轮询系统。

### 2.5 回答去重与输入保留

- 问助手主操作只保留一个“发送”按钮，统一调用 `POST /matters/intake`；网页不再同时
  请求 `/asks` 和事项入口，也不按关键词猜测保存行为。
- `intent=question` 且带回答时直接显示服务器这一份回答，不打开空事项面板；
  `draft` 结果打开现有待确认面板；`matter_intent_unclear` 显示服务器补充问题并保留原输入。
- 处理中显示明确状态。超时或未知结果保留原输入和同一操作标识，可查询服务器结果
  或用同一次操作继续，不换标识重复创建。
- 事项详情“补充进展”收到普通问题时打开“助手回答”面板，保留原问题与回答。
- 统一回答、补充问题和处理中状态读取 `GET /matters/intake`，单条结果可读取
  `GET /matters/intake/{local_run_id}`。本机旧缓存只作为服务端历史的兼容补充，
  相同运行标识或相同问答不会重复显示。
- 用户回答补充问题时携带 `continuation_run_id`，服务端保存的候选、已填写事项和地点会
  继续沿用；补充新信息使用新的幂等键，不覆盖原请求。
- 事项详情“补充进展”收到普通问题时打开“助手回答”面板，保留原问题与回答。
- 待确认草稿和多候选事项从服务器恢复，多候选在面板中直接选择，不要求重输背景。
- 首次新输入生成草稿时轻柔打开面板；重新进入页面只列出来自服务器的待确认内容，不自动
  反复弹出。切换账号时统一历史、待确认草稿和页面临时状态会清空并重新读取对应账号数据。

### 2.6 路线文字卡

- 今天页、事项详情和草稿确认面板使用白色圆角文字卡展示已返回的路线证据，不绘制地图。
- 有冲突测算时显示相邻安排、出发/到达时间、服务器耗时、间隔和判断原因；没有完整起点、
  出行方式或天气时明确显示未提供，不用独立通勤建议补齐。
- `route.status=unverified`、`eta_status=unverified` 都显示“路程未核实”；时间充裕、
  可能赶不上和路线不可用使用文字区分，颜色只作辅助。
- 地点输入支持 `POST /commute/places/search`，按名称、地址、城市展示候选，默认不选第一项；
  用户明确选择后通过 `POST /commute/places/confirm` 写入草稿并重新计算冲突。
- 地点候选按 GCJ-02/WGS-84/未知坐标来源区分。地图按钮只在坐标来源与目标地图兼容时使用坐标，
  否则按地址搜索；高德结果优先打开高德链接，未点击前不向外部地图发送位置。
- 事项详情可以从上一项安排或明确选择的起点调用 `POST /commute/estimate`，显示服务器返回的
  方式、耗时、距离、步行距离、换乘、费用、时间依据和起点依据；未来路线标明计划时间估算。
- 对应日期天气字段当前未出现在日程路线结果中，因此页面不补天气图标或确定天气结论。

### 2.7 数据连接入口

- “我的”将应用内日程与提醒、日历订阅、手机资料上传分为三张独立卡片，默认只显示状态
  和摘要，详细说明展开后查看。
- 日历订阅接入查询、创建、更新范围、关闭和重新生成。用户先选择事项并明确操作，才请求
  私人链接；链接只在创建/重新生成响应中显示一次，不写入普通浏览器缓存。
- 重新生成前提示旧链接失效和手机可能需重新订阅；关闭后提示已下载内容可能需要自行移除。
  点击打开只说明“已打开添加步骤”，最近读取时间是服务器收到读取的时间，不写成手机同步完成。
- 日历订阅只生成只读日程，不生成提醒标记；独立待办提醒仍属于应用内记录。
- 快捷指令上传接入来源创建、一次性设备凭据生成、使用记录和撤销。凭据只在生成响应中显示，
  不写日志或普通缓存；生成凭据不等于上传成功。
- 上传来源读取最近成功上传时间、授权范围和失败原因，管理入口继续进入现有来源详情。
- 页面提示排除本应用订阅日历、不要输入 Apple 账号密码、不要把连接凭据放进截图或分享链接；
  没有可验证的快捷指令文件时不提供安装或下载按钮。

## 4. 仍受限制的事项

1. 今天页路线摘要只返回方式、耗时、取得时间和起点依据；完整换乘、费用和距离保存在路线
   结果中，但尚未提供独立读取接口，刷新后事项详情只能显示摘要。
2. 提醒只表示服务器保存了待发记录，没有送达回执；页面不显示“已送达”。
3. 苹果端导入日程只能回到苹果端修改，Web 不绕过服务端只读限制。
4. 日历订阅当前使用本地 API 基址生成链接，手机无法访问 `localhost`；需配置手机可达的
   `calendar_public_base_url` 后才能完成真实订阅。
5. 快捷指令还没有可验证的分发文件或安装链接，因此页面只提供配置步骤。
6. 日历提醒是否按时出现、手机是否自动刷新、订阅邮件/锁屏行为，以及快捷指令稳定编号和
   更新时间是否可读，仍需真实设备验证。
7. 本轮没有真实模型、真实高德请求、真实私人链接、真实快捷指令上传、真实通知或真实用户数据验证。

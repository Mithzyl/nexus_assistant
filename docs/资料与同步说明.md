## 1. 规划对资料与同步的要求

| 要求 | 原文位置 | 原文关键内容 |
|---|---|---|
| Web 端数据自闭环 | §1 | 系统内置独立的「日程表」与「提醒事项」数据库表；完全不连 iOS 客户端也能处理事项、日程、提醒与通勤检查 |
| 数据来源字段 | §1 | `source: web_native \| ios_eventkit \| ios_reminders` |
| iOS 增量上传 | §4 | `POST /api/v1/sync/ios/snapshot`，接收 EventKit 日历与提醒变更，带 `external_id` 和 `last_modified_at`，用于冲突比对 |
| iOS 待回写拉取 | §4 | `GET /api/v1/sync/ios/pending-actions`；Web 端授权写入后状态为 `web_confirmed_pending_ios`，iOS 写入后回调 `ios_synced` |
| 同步状态机 | 模块一 | 每条日程/提醒包含 `sync_status`：`local_only` / `pending_ios` / `ios_synced` |
| 通勤测算抽象 | §4 | 统一接口 `/api/v1/commute/estimate`；Web 调网页地图 API，iOS 未来上传 MapKit 结果，返回结构一致 |
| 冲突检查数据范围 | §3、模块二 | 检查内置日程与已上传 iOS 日程；新时间/地点变化时拉取前后 3 小时日程，余量不足 15 分钟触发预警 |

## 2. 现有资料上传能力

### 2.1 已有接口

| 接口 | 作用 | 代码位置 |
|---|---|---|
| `POST /api/v1/data-sources` | 创建来源（calendar / reminders / notes） | `services/assistant-api/src/assistant_api/routers/data_sources.py` |
| `PATCH /api/v1/data-sources/{source_id}` | 修改显示名、上传开关、助手授权、字段授权、范围 | 同上 |
| `POST /api/v1/data-sources/{source_id}/sync` | 上传一批设备内容副本 | 同上 |
| `GET /api/v1/content`、`GET /api/v1/content/{item_id}` | 查询已上传内容 | 同上 |
| `DELETE /api/v1/data-sources/{source_id}/items` | 删除已上传副本、保留来源 | 同上 |
| `DELETE /api/v1/data-sources/{source_id}` | 删除来源与副本 | 同上 |

### 2.2 现有字段与规则

来源与内容模型在 `models/content.py`：

- `content_sources`：`source_type`、`device_id`、`display_name`、`sync_enabled`、`assistant_enabled`、`upload_fields_json`、`last_sync_at`、`last_sync_status`。
- `content_source_scopes`：`scope_key`、`active`、`activated_at`。
- `content_items`：`kind`、`external_id`、`scope_key`、`version`、`source_updated_at`、`synced_at`、`deleted_at`、`title`、`body`、`starts_at`、`ends_at`、`due_at`、`status`、`location`、`tags_json`、`payload_json`。
- `content_sync_batches`：`batch_id` 幂等统计。

字段白名单（`docs/backend-integration/12-设备内容同步契约.md`）：

- calendar：`title/start/end/location/notes/status`
- reminders：`title/due/notes/status`
- notes：`title/body/tags`

### 2.3 现有上传与规划的区别

| 维度 | 现有实现 | 规划要求 | 差异 |
|---|---|---|---|
| 方向 | iOS → PA 的只读副本上传 | 新增 iOS → PA 快照，以及 PA → iOS 待写入 | 现有没有写回 |
| 路径 | `/api/v1/data-sources/{source_id}/sync` | `/api/v1/sync/ios/snapshot`、`/api/v1/sync/ios/pending-actions` | 路径与契约不同 |
| 时间字段 | `source_updated_at`、`updated_at` | `last_modified_at` | 字段名不同 |
| 状态 | 来源级 `last_sync_status`（ok/failed/items_deleted） | 记录级 `sync_status`（local_only/pending_ios/ios_synced） | 层级与语义不同 |
| 写回 | 明确不写回 EventKit | 需要待写入队列与 `ios_synced` 回调 | 完全缺失 |
| 冲突 | 版本号拒绝旧记录，不做双向合并 | 快照用于后台冲突比对 | 只有单向版本控制 |

**结论**：现有上传能力可以复用于“把 iOS 日历/提醒读进 PA”，但不能当作 `snapshot` 或 `pending-actions` 已完成。

## 3. 内置日程与提醒

| 能力 | 现有位置 | 可复用 | 尚缺 |
|---|---|---|---|
| 日程表 | `models/business.py` 的 `schedules`：`title`、`starts_at`、`ends_at`、`location`、`status`、`source_run_id` | 表结构、时间字段、按日期窗口查询 | 创建/修改/删除接口；`source`；`sync_status`；与事项关联；提醒 |
| 提醒表 | 无 | `tasks.due_at` 只能表达截止；`content_items.due_at/status` 可保存上传副本 | 独立提醒记录、提醒状态、写入队列 |
| 日程读取 | 只读工具 `personal_assistant.list_calendar_events`，会合并 `schedules` 与已授权上传的 `calendar_event` | 读取路径、字段授权、账号隔离 | 用户页面直接读写日程；冲突扫描 |
| 提醒读取 | 只读工具 `personal_assistant.list_tasks`，合并 `tasks` 与已授权上传的 `reminder` | 读取路径 | 提醒写入、提醒状态、提醒与日程/事项关联 |
| 写入 API | 无 | 现有鉴权、幂等、错误码模式 | 全部 |

**结论**：日程表可复用一部分字段与读工具；提醒表、写入接口和同步状态机都还没有。

## 4. 待写入操作（pending actions）

规划要求：

1. 用户在 Web 端确认写入日历/提醒后，记录状态为 `web_confirmed_pending_ios`。
2. iOS 客户端打开时拉取待写入队列。
3. iOS 写入苹果系统日历/提醒后回调，状态变为 `ios_synced`。

当前实现：

- 没有待写入队列表、没有 `pending-actions` 路由、没有 `web_confirmed_pending_ios` 或 `ios_synced` 状态。
- 现有 `content_sources` 的同步是“设备上传副本”，没有反向写入。
- 现有 Bark 通知与通勤提醒走的是 PA 自己的通知 outbox（`models/commute.py`），与系统日历/提醒写回无关，不能混为一谈。

**结论**：待写入操作**尚未开发**。纯网页 `local_only` 与验收第 6 条统一“待 iOS 客户端同步”文案之间存在原文歧义，见规划附录 C-4。此处不自行决定状态或回写授权，也不能显示“已写入 iPhone 系统日历”。

## 5. 通勤测算

| 规划要求 | 现有实现 | 可复用 | 缺口 |
|---|---|---|---|
| `/api/v1/commute/estimate` 统一路线耗时接口 | 无该路径；OpenAPI 中没有 | — | 独立接口、统一请求/响应 |
| 路线 ETA 计算 | `commute/providers/base.py` 的 `RouteEtaProvider`；`maps_eta.py` 调地图服务；`mock.py` 用于开发测试 | Provider 抽象、ETA 解析、超时/错误分类、mock | 任意起终点即时查询；Web 端网页地图 API 的统一封装 |
| 测算入口 | `POST /api/v1/commute-plans/{plan_id}/checks` 在检查流程内测算并保存建议，已支持 `route_snapshot` 上传 MapKit 结果（`mapkit_client`） | 检查幂等、阶段状态、建议保存 | 独立估算；与事项日程联动的冲突检查 |
| 路线可用性 | `GET /api/v1/commute/runtime` 报告 Provider 是否可用 | 前端可读取真实状态 | 不能把“页面有地图”当成“已获取 ETA” |
| 前后 3 小时冲突与 15 分钟余量 | 无；现有只比较单个计划的 ETA 与目标到达时间及缓冲 | 缓冲时间字段（`buffer_minutes`、`rain_extra_buffer_minutes`） | 日程窗口扫描、余量规则、冲突分级 |

**结论**：通勤测算的**底层能力存在**（Provider + 检查流程 + ETA 归一化），但规划要求的**独立接口和冲突规则尚未实现**。据 2026-10-25 记录，8010 环境没有可用的服务端路线 Provider，历史建议只能读取，不能宣称能独立完成新的真实路线分析。

## 6. 逐项复用判断

回写结果回调、失败与重复反馈、各同步路径的方向和适用资料，以及网页独立提醒的交付场景，见规划附录 D；此处不补设接口、状态、授权或通知技术。上文待写入流程对应原文 §4，不能据此取消 `local_only` 的纯网页场景。
